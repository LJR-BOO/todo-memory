## 第 0 章 先建立世界观（20 分钟，最重要）

### 0.1 这个项目到底是什么？

它是一个**后端服务（API 服务）**，也就是一台"专门处理别人请求的电脑程序"。

- 别人（前端网页、手机 App、Postman）通过**网址**向它发请求；
- 它根据网址去**查数据库 / 写数据库**；
- 然后把结果**打包成 JSON** 还回去。

用餐厅打比方：

| 角色 | 比喻 | 项目里的东西 |
|------|------|-------------|
| 客户端 | 顾客 | 浏览器 / Postman / 前端 |
| HTTP 请求 | 顾客点单（"我要一份宫保鸡丁"） | 带方法的 URL，如 `POST /todo/` |
| FastAPI | 前台服务员 | 负责接单、按菜单找厨师、端菜 |
| 路由 (Router) | 菜单分区 | `routers/` 里的接口定义 |
| 视图函数 | 厨师 | 真正干活的 Python 函数 |
| 数据库 MySQL | 后厨仓库 | 存用户、存待办的"仓库" |
| Redis | 前台小黑板 | 记下常用信息，下次直接念，不用再跑仓库 |
| JSON 响应 | 端上桌的菜 | `{"code":200, "msg":"...", "data":{...}}` |

### 0.2 HTTP 请求长什么样？

一个请求由几部分组成：

- **方法**：GET（查）、POST（增）、PUT（改）、DELETE（删）—— REST 风格里，方法表示"动作"；
- **路径**：`/auth/login`、`/todo/1` —— 表示"对哪个资源动手"；
- **请求头 (Headers)**：比如 `Authorization: Bearer <token>` —— 用来告诉后端"我是谁"；
- **请求体 (Body)**：POST/PUT 时携带的数据，比如注册时带的 `{"username":"a","password":"b"}`。

后端处理完，返回一个**响应**：状态码（200 成功 / 401 没登录 / 422 参数不对 / 500 服务器炸了）+ 响应体（JSON）。

### 0.3 技术栈一句话

> FastAPI（接请求的框架）+ SQLAlchemy（把 Python 类和数据库表互相翻译的 ORM）+ MySQL（存数据）+ Redis（缓存）+ JWT（登录通行证）+ bcrypt（密码加密）+ Alembic（改数据库表结构的工具）+ Docker（打包部署）。

后面每一章都会逐个拆开讲。

## 第 2 章 四个核心概念，用大白话讲透

在逐行看代码之前，必须先懂这四个词。它们是看懂整个项目的前提。

### 2.1 路由（Router）：接口的"地址簿"

每个接口 = 一个"方法 + 路径"。比如：

```python
@router.post("/login")        # 表示：处理 POST /auth/login 这个请求
def login(...): ...
```

`router = APIRouter(prefix="/auth")` 表示这个文件里所有路径前面都自动加 `/auth`。
所以 `routers/auth.py` 里的 `"/login"` 实际对外是 `/auth/login`。
`main.py` 里 `app.include_router(auth_router)` 就是把这本"地址簿"装进总机。

### 2.2 Pydantic（Schemas）：数据的"格式检查员"

前端传来的数据是乱的，Pydantic 负责**校验**并**转成 Python 对象**。

```python
class TodoCreate(BaseModel):
    title: str = Field(min_length=1, max_length=200)
```

意思是：`title` 必须是字符串，长度 1~200。如果前端传 `title=123` 或空字符串，Pydantic 直接**拒单**，FastAPI 返回 **422**（参数校验失败）。

它还有两个常用本领：

- `model_dump()`：把 Pydantic 对象变成**字典**（方便传给 ORM 建对象）；
- `model_validate(obj)`：从 ORM 对象**构造**响应模型（把数据库行变成能返回的格式）。

### 2.3 SQLAlchemy ORM：数据库表的"翻译官"

数据库里存的是**表**（行列结构），Python 里想用**对象**操作。ORM 就是两者之间的翻译：

| 数据库 | Python（ORM） |
|--------|--------------|
| 表 `sys_user` | 类 `User` |
| 一行数据 | 一个 `User` 对象 |
| 一个字段 `username` | `user.username` 属性 |
| 写 SQL 查询 | `db.query(User).filter(...)` |

所以 `models/user.py` 里写的 `__tablename__ = "sys_user"` + 一堆 `Column(...)`，就是**表的设计图纸**：每个 `Column` 对应一列，`String(50)` 是类型和长度，`unique=True` 是唯一约束，`ForeignKey` 是外键。

### 2.4 依赖注入（Depends）：FastAPI 自动帮你"备菜"

很多接口函数都需要"数据库会话"、"当前用户"。如果每个函数自己创建，代码会又臭又长。FastAPI 的 `Depends` 机制是：

> **你只需要在函数参数里写 `db: Session = Depends(get_db)`，FastAPI 就会自动调用 `get_db()`，把结果传进来。用完全自动清理。**

```python
def create_todo(todo_data: TodoCreate, db: Session = Depends(get_db),
                user_id: int = Depends(get_current_user_id)):
```

FastAPI 看到这三个参数，会**先**按顺序准备好：
1. `todo_data`：用 Pydantic 校验请求体；
2. `db`：调用 `get_db()` 拿到数据库会话；
3. `user_id`：调用 `get_current_user_id()` → 里面又调用 `get_current_user()` → 又调用 `oauth2_scheme()` 从请求头拿 token……

这就是**依赖可以层层嵌套**。面试官问"Depends 怎么工作"，就答：FastAPI 在调用视图函数前，自动解析每个 `Depends`，把结果注入参数，依赖之间可以继续依赖其他依赖，形成一个"依赖树"。

## 第 4 章 数据库层：models 和 db/base.py

### 4.1 models/user.py：用户表设计图纸（14 行）

```python
1  from datetime import datetime
2  from sqlalchemy import Column, Integer, String, DateTime, func
3  from sqlalchemy.orm import relationship
4  from db.base import Base
5
6  class User(Base):
7      __tablename__ = "sys_user"
8
9      id = Column(Integer, primary_key=True, autoincrement=True)
10     username = Column(String(50), unique=True, nullable=False, index=True)
11     hashed_password = Column(String(128), nullable=False)
12     create_time = Column(DateTime, server_default=func.now(), default=datetime.utcnow)
13
14     todos = relationship("Todo", back_populates="user")
```

- L4：`User` 继承 `Base`（来自 `db/base.py` 的 `declarative_base()`），意思是"我是数据库模型"。
- L7：`__tablename__` 指定数据库里表的名字叫 `sys_user`。
- L9：`id` —— 主键，自增。每行数据唯一身份证。
- L10：`username` —— 最长 50 字符的字符串；`unique=True` 用户名不能重复；`nullable=False` 必填；`index=True` 建索引，查询快。
- L11：`hashed_password` —— 存的是 **bcrypt 加密后的密文**（不是明文密码！），长度 128。
- L12：`create_time` —— 创建时间。**两个默认值**：
  - `server_default=func.now()`：数据库层面生成（不走 ORM 也生效）；
  - `default=datetime.utcnow`：Python 层面生成（ORM 插入时生效）。
  - 两个都写，保证无论哪条路径都有时间。
- L14：`relationship("Todo", back_populates="user")` —— 声明"一个用户有多个待办"的关系。配合 `Todo` 表里的反向声明，就能用 `user.todos` 拿到这个用户的全部待办。

### 4.2 models/todo.py：待办表设计图纸（15 行）

```python
6  class Todo(Base):
7      __tablename__ = "todos"
8
9      id = Column(Integer, primary_key=True, autoincrement=True, index=True)
10     title = Column(String(200), nullable=False)
11     description = Column(String(500), nullable=True)
12     is_done = Column(Boolean, default=False)
13     create_time = Column(DateTime, server_default=func.now(), default=datetime.utcnow)
14     user_id = Column(Integer, ForeignKey("sys_user.id"), nullable=False)
15     user = relationship("User", back_populates="todos")
```

- L9~13：和 User 类似。`description` 可空（`nullable=True`）；`is_done` 默认 `False`（没完成）。
- L14：**外键** `ForeignKey("sys_user.id")` —— 每条待办必须属于某个用户。这就是"用户数据隔离"的根基：待办表用 `user_id` 挂到用户表。
- L15：反向关系声明，和 User 表的 `relationship` 配对（`back_populates` 两边互相指认）。

**为什么外键 + 查询条件 = 数据隔离？**
因为 `todos.user_id` 是"这条待办属于谁"，而所有接口里查待办都强制带 `filter(Todo.user_id == user_id)`，`user_id` 来自 token。所以 A 用户永远拿不到 B 用户的待办。

### 4.3 db/base.py：数据库连接层（23 行，重点！）

```python
1  from sqlalchemy import create_engine
2  from sqlalchemy.orm import declarative_base, sessionmaker
3  from config.settings import settings
4
5  engine = create_engine(
6      settings.database_url,
7      echo=False,
8      pool_pre_ping=True
9  )
```

- L5~9：`create_engine` 创建**数据库引擎**。`settings.database_url` 是 `config/settings.py` 里拼好的 MySQL 连接串（`mysql+pymysql://用户:密码@地址:端口/库名`）。`pool_pre_ping=True`：每次拿连接前先"ping"一下，防止拿到已断开的死连接。
- 引擎是**全局只有一个**的连接池：多个请求复用里面的连接，而不是每个请求都新建连接（新建连接很慢）。

```python
11 Base = declarative_base()
```

- L11：创建所有模型类的**共同父类**。所有 `class User(Base)` 都是它的子类。`Base.metadata` 收集了所有模型的定义，Alembic 就是靠它知道"有哪些表要建"。

```python
13 SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

- L13：`sessionmaker` 是"会话工厂"。`SessionLocal()` 每次调用就**新开一个数据库会话（Session）**。
  - `autocommit=False`：不会自动提交，必须手动 `db.commit()` 才真正写库（**这很重要**：不然你以为存了，其实没存）；
  - `autoflush=False`：查询前不会偷偷把未保存的修改先刷进数据库（保持行为可控）。

```python
15 def get_db():
16     db = SessionLocal()
17     try:
18         yield db
19     except Exception:
20         db.rollback()
21         raise
22     finally:
23         db.close()
```

这是整个项目**最核心的 9 行**，面试必问，逐行讲：

- L16：创建新会话 `db`（一次请求一个会话）。
- L17~18：`try: yield db` —— **`yield` 是关键**：
  - `get_db` 是**生成器函数**。执行到 `yield` 会"暂停"，把 `db` 交出去；
  - FastAPI 拿到 `db` 注入给视图函数，视图函数整个处理过程都在 `try` 的保护范围内；
  - 请求处理完，FastAPI 会让生成器"恢复"，继续往下执行。
  - **为什么用 `yield` 而不是 `return`？** 如果 `return db`，函数一结束，后面没法做收尾（关会话）；而且生成器让"借出"和"收回"包住整个请求生命周期。
- L19~21：`except Exception: db.rollback(); raise` —— 处理过程中**任何异常**：
  - `db.rollback()`：回滚事务，撤销这次请求里所有没提交的数据库修改（防止半截数据写进库）；
  - `raise`：把异常**原样继续抛出去**，交给 main.py 里的全局异常处理器。
- L22~23：`finally: db.close()` —— **无论成功还是失败**，最后一定关闭会话，把连接还给连接池。`finally` 保证"一定执行"。

**get_db 面试三连问**：
1. 为什么用 `yield`？→ 生成器依赖，让会话的生命周期=请求的生命周期，借出后还能收尾。
2. `finally` 里做什么？→ `db.close()` 关闭会话、归还连接。

### 5.1 密码加密：get_password_hash 和 verify_password

```python
15 oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")
```

- L15：告诉 FastAPI："从 `Authorization: Bearer xxx` 请求头里提取 token"。`tokenUrl` 是给 Swagger 文档的"获取 token 的地址"。
- **副作用**：如果请求头里没有 token，FastAPI 会**自动返回 401**（"Not authenticated"）——这就是你没带 token 访问 `/todo/*` 时看到的 401 的来源之一。

```python
17 def verify_password(plain_password, hashed_password):
18     try:
19         return bcrypt.checkpw(plain_password.encode("utf-8"), hashed_password.encode("utf-8"))
20     except ValueError:
21         return False
```

- L19：`bcrypt.checkpw(明文, 密文)` —— 用同一个盐重算哈希，比对是否一致，返回 True/False。
  - `.encode("utf-8")`：bcrypt 要的是**字节**，不是字符串。
- L20~21：`except ValueError: return False` —— 如果数据库里存的密文格式不对（比如被截断、不是 bcrypt 格式），`checkpw` 会抛 ValueError。**捕获后返回 False 而不是让程序崩**（否则登录接口会变成 500）。

```python
23 def get_password_hash(password):
24     # bcrypt 限制 72 字节
25     if len(password.encode("utf-8")) > 72:
26         raise BizException(code=CODE_PARAM_ERROR, msg="密码过长，最多72字节（约24个中文字符）")
27     return bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")
```

- L25~26：**为什么先做长度校验？**
  - bcrypt 的算法**只使用前 72 字节**，超过 72 字节的密码，有的实现会**直接抛异常**（`password cannot be longer than 72 bytes`）。
  - 如果不拦截，这个异常会一路冒泡，被 main.py 的兜底处理器接住 → 返回 **500**（服务器内部错误）。
  - 主动拦截，返回**业务错误 400**"密码过长"——体验更好，也避免 500。
  - 字节 ≠ 字符：一个中文占 3 字节，所以约 24 个中文字符就到 72 字节了。
- L27：`bcrypt.gensalt()` 生成**随机盐**（同样的密码每次加密结果都不同），`hashpw` 算出密文，`.decode("utf-8")` 转成字符串存库。

### 5.2 签发 token：create_access_token

```python
29 def create_access_token(data: dict, expires_delta: Optional[timedelta] = None):
30     to_encode = data.copy()
31     expire = datetime.utcnow() + (expires_delta or timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES))
32     to_encode.update({"exp": expire})
33     return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=settings.ALGORITHM)
```

- L30：`data.copy()` —— 复制一份，**不改调用者传进来的原字典**。
- L31：算过期时间 = 现在 + 30 分钟（默认，来自 `.env` 的 `ACCESS_TOKEN_EXPIRE_MINUTES`）。
- L32：把 `exp`（过期时间）塞进 payload。JWT 解码时如果过了这个时间会自动失败。
- L33：`jwt.encode(payload, 密钥, 算法)` —— 用 `SECRET_KEY` 和 HS256 算法签名。**签名 = 防篡改**：密钥只有服务器知道，别人改不了 payload（改了签名就对不上，解码直接失败）。

### 5.3 校验登录态：get_current_user（重点中的重点）

```python
35 def get_current_user(token: str = Depends(oauth2_scheme), db: Session = Depends(get_db)):
36     credentials_exception = HTTPException(
37         status_code=status.HTTP_401_UNAUTHORIZED,
38         detail="无效的认证信息",
39         headers={"WWW-Authenticate": "Bearer"},
40     )
41     try:
42         payload = jwt.decode(token, settings.SECRET_KEY, algorithms=[settings.ALGORITHM])
43         sub = payload.get("sub")
44         if sub is None:
45             raise credentials_exception
46         user_id = int(sub)
47     except (JWTError, TypeError, ValueError):
48         raise credentials_exception
49     user = db.query(User).filter(User.id == user_id).first()
50     if user is None:
51         raise credentials_exception
52     return user
```

这是"判断你有没有登录"的函数，**每一步都要能讲**：

- L35：两个参数都是依赖注入：
  - `token` ← `oauth2_scheme`：从请求头 `Authorization: Bearer xxx` 里取出 token；
  - `db` ← `get_db`：数据库会话。
- L36~40：先准备好一个"标准 401 异常"对象，后面所有"认证不过"的情况都抛它。`WWW-Authenticate: Bearer` 头是 HTTP 规范要求，告诉客户端"请用 Bearer 方式重新认证"。
- L42：`jwt.decode(token, 密钥, 算法)` —— **一次做三件事**：
  1. 验证签名（用 SECRET_KEY 重算比对，防篡改）；
  2. 验证过期时间（`exp` 已过 → 抛 `JWTError`）；
  3. 解出 payload（里面有 `sub` 和 `exp`）。
  - 签名不对 / 过期 / 格式坏 → 都会抛 `JWTError`。
- L43~45：`payload.get("sub")` 取用户 id（签发时放进去的）。**没有 `sub`**（token 合法但没有用户信息）→ 抛 401。
- L46：`int(sub)` —— 把字符串转回整数。**为什么要转？** 签发时为了符合 JWT 规范（`sub` 必须是字符串）存的是 `str(user.id)`，查库时 `User.id` 是整数，所以要转回来。
- L47~48：`except (JWTError, TypeError, ValueError)` —— 解码失败、`int()` 转换失败（比如 `sub` 是乱码）都算"无效认证"，抛 401。**为什么抓 TypeError 和 ValueError？** 因为 `int(sub)` 可能抛 ValueError，`sub` 缺失时 `payload.get` 可能抛 TypeError——兜底，别让这些变成 500。
- L49：`db.query(User).filter(User.id == user_id).first()` —— 拿 user_id 去数据库查这个用户。**为什么要查库？** JWT 本身无状态、不查库，但这里要确认"这个用户**还存在**"（比如用户被删了，token 虽然有效但人不在了）。
- L50~51：用户不存在 → 抛 401。
- L52：一切正常 → 返回**用户对象**。调用者就能用 `current_user.id`、`current_user.username` 了。

**小结（能背）**：取 token → 解码（验签+验过期）→ 取 sub → 转 int → 查库确认用户存在 → 返回用户。任何一步失败 → 401。

### 6.2 routers/auth.py：登录

```python
42 # 注意：必须放在 /{todo_id} 之前注册，否则 DELETE /todo/clear 会被 /{todo_id} 匹配而返回 422
43 @router.delete("/clear")
44 def clear_all(db: Session = Depends(get_db), user_id: int = Depends(get_current_user_id)):
45     db.query(Todo).filter(Todo.user_id == user_id).delete()
46     db.commit()
47     cursor = 0
48     while True:
49         cursor, keys = redis_client.scan(cursor=cursor, match=f"{CACHE_PREFIX}{user_id}:*", count=100)
50         if keys:
51             redis_client.delete(*keys)
52         if cursor == 0:
53             break
54     return success(msg="清空成功")
```

- **L42 的注释是踩坑记录**：FastAPI 按**注册顺序**匹配路径。`/clear` 如果写在 `/{todo_id}` 后面，请求 `DELETE /todo/clear` 会先被 `/{todo_id}` 匹配，把 `clear` 当整数解析 → 失败返回 422。所以静态路径（`/clear`）必须放在动态路径（`/{todo_id}`）**前面**。
- L45：一条 SQL 删除当前用户全部待办（`delete()` 是批量删除，不用逐条）。
- L47~53：**用 `scan` 删缓存，不用 `keys`**：
  - `KEYS todo:1:*` 会一次性全库扫描，**阻塞 Redis**（Redis 是单线程），数据多时整个服务卡死；
  - `SCAN cursor ...` 是**游标分页**扫描，每次拿一批（count=100），不阻塞；游标回到 0 表示扫完。
  - 这是高频面试点："为什么用 scan 不用 keys？"

- `TodoResponse`：响应格式，`from_attributes = True`。

**schemas/common.py**
- `BaseResponse`：泛型包装 `{code, msg, data}`，`Generic[T]` 表示 data 可以是任意类型。项目中实际响应用的是 `utils/response.py`，这个文件更多是规范示例。

**一句话**：schemas 管"请求长什么样、响应长什么样"，Pydantic 在进接口时校验、出接口时过滤。

### 7.2 utils/response.py：统一响应

```python
6  def success(data=None, msg="操作成功"):
7      encoded_data = jsonable_encoder(data)
8      return JSONResponse(status_code=200, content={"code": CODE_SUCCESS, "msg": msg, "data": encoded_data})
13 def fail(code: int, msg: str):
14     return JSONResponse(status_code=200, content={"code": code, "msg": msg, "data": None})
```

- `success` / `fail` **HTTP 状态码都是 200**，业务状态放 body 的 `code` 里。
- `jsonable_encoder`：把 datetime、ORM 对象等转成**能 JSON 序列化**的类型（否则直接返回会报错）。
- 好处：前端只认一种格式 `{code,msg,data}`，统一处理成功/失败。

### 7.3 utils/exceptions.py：业务异常

```python
1  class BizException(Exception):
2      def __init__(self, code: int, msg: str):
3          self.code = code
4          self.msg = msg
5          super().__init__(msg)
```

- 自定义异常，带 `code` 和 `msg`。业务代码里 `raise BizException(code=400, msg="...")`，被 main.py 的 `biz_exception_handler` 接住，统一转成 `fail(code, msg)`。
- **为什么不用 HTTPException？** HTTPException 是 FastAPI 原生的（返回真实 HTTP 状态码）；BizException 是项目自定义的"业务错误通道"（HTTP 200 + body code）。两种都能用，本项目混用了：认证用 HTTPException(401)，业务校验用 BizException。

### 7.4 utils/logger.py：日志中间件

```python
8  async def log_middleware(request: Request, call_next):
9      start = time.time()
10     response = await call_next(request)
11     cost = round(time.time() - start, 3)
12     logger.info(f"{request.method} {request.url.path} | 状态:{response.status_code} | 耗时:{cost}s")
13     return response
```

- L10：`await call_next(request)` —— **把请求放行**给下一层（路由），等响应回来继续执行。这是中间件的标准写法：前置逻辑（计时开始）→ 放行 → 后置逻辑（算耗时、记日志）。
- 你在启动服务的终端里看到的 `POST /todo/ | 状态:200 | 耗时:0.012s` 就是它打的。

### 7.5 constants/error_codes.py

```python
CODE_SUCCESS = 200
CODE_PARAM_ERROR = 400
CODE_NOT_FOUND = 404
CODE_SERVER_ERROR = 500
CODE_DB_ERROR = 50001
```

- 错误码常量。**背下来**：200 成功 / 400 参数或业务错误 / 404 不存在 / 500 服务器内部错误 / 50001 数据库异常。
- 注意区分：body 里的 `code`（业务码）和 HTTP 状态码（传输层码）是两回事。

### 7.6 config/settings.py：配置

```python
5  class Settings(BaseSettings):
6      DB_HOST: str = Field(default="127.0.0.1")
        ...  # 数据库、Redis、JWT 的配置项，都有默认值
24     class Config:
25         env_file = ".env"
26         extra = "ignore"
28     @model_validator(mode="after")
29     def _reject_insecure_secret(self):
30         if self.SECRET_KEY in ("your-secret-key-change-me", "change-me-in-production", ""):
31             raise ValueError("SECRET_KEY 未配置或仍为默认值，请在 .env 中设置强随机密钥")
32         return self
35     @property
36     def database_url(self):
37         return f"mysql+pymysql://{self.DB_USER}:{self.DB_PASSWORD}@{self.DB_HOST}:{self.DB_PORT}/{self.DB_NAME}?charset=utf8mb4"
39 settings = Settings()
```

- L5~22：`BaseSettings` 自动从 `.env` 文件读配置（`env_file=".env"`），有默认值兜底。
- L28~32：`model_validator(mode="after")` —— 加载完成后**校验**：`SECRET_KEY` 如果是默认值就抛错，**应用直接启动失败**。为什么？SECRET_KEY 泄露 = 任何人都能伪造 token（见 5.2），宁可启动失败也不能带默认密钥上线。
- L35~37：`@property database_url` —— 一个"假属性"，用配置拼出 MySQL 连接串。`db/base.py` 的 `create_engine(settings.database_url)` 就是用它。
- L39：**模块加载时就创建好全局唯一的 settings 对象**，其他文件 `from config.settings import settings` 拿到的都是同一个。

### 7.7 alembic/：数据库迁移

- **是干什么的**：改表结构不能手改数据库（多人协作会乱）。Alembic 把"模型的变更"记录成**版本化迁移文件**，`alembic upgrade head` 一条命令把库升级到最新。
- `alembic/env.py`：告诉 Alembic"看哪些表"（`target_metadata = Base.metadata`，即 models 里所有模型）和"连哪个库"（`get_url()` 从环境变量拼连接串）。
- `alembic/versions/af09c4458704_init_tables.py`：第一个迁移文件：
  - `upgrade()`：**建表**（sys_user、todos，含外键和索引）；
  - `downgrade()`：**删表**（回退用）；
  - `revision` / `down_revision`：每个迁移文件的"身份证"和"上一个是谁"，串成一条迁移链。
- 命令：`alembic upgrade head`（升级到最新）/ `alembic downgrade -1`（回退一步）。
- **为什么用 Alembic 而不是手动建表？** 版本可控、可回滚、团队同步、和生产环境保持一致。

## 第 8 章 调用链路：一个请求从进门到出门的完整故事

面试官最爱问："一个请求进来，都经历了什么？"——把下面这个故事背下来。

### 8.1 全链路总览图（以 `POST /todo/` 为例）

```
客户端（前端/Postman）
  │  发请求：POST http://127.0.0.1:8000/todo/
  │         Header: Authorization: Bearer <token>
  │         Body:   {"title":"写作业"}
  ▼
① uvicorn（Web 服务器，监听 8000 端口，把 HTTP 报文解析成 Request 对象）
  ▼
② 中间件（按注册顺序执行）
  ├─ log_middleware（utils/logger.py）：记录开始时间 → 放行
  └─ CORSMiddleware：检查跨域，加响应头
  ▼
③ FastAPI 路由匹配：按注册顺序找哪个函数处理 /todo/
  └─ 找到 routers/todo.py 的 create_todo
  ▼
④ 依赖注入（FastAPI 先解析函数参数，全部准备好才调用函数）
  ├─ todo_data ← Pydantic 校验请求体（schemas/todo.py TodoCreate）
  ├─ db ← get_db()（db/base.py）：new 一个 Session，yield 借出
  └─ user_id ← get_current_user_id()（utils/auth.py）
        └─ 依赖 get_current_user()
             ├─ oauth2_scheme：从 Header 取 token（没有→401）
             ├─ jwt.decode：验签 + 验过期（失败→401）
             ├─ 取 sub → int 转 user_id（异常→401）
             └─ 查库确认用户存在（不存在→401）
             返回 user → 取 .id
  ▼
⑤ 视图函数 create_todo 执行：
  Todo(**todo_data.model_dump(), user_id=user_id) → db.add → db.commit（写MySQL）→ db.refresh
  ▼
⑥ success(data=...)（utils/response.py）：
  把结果包成 {"code":200, "msg":"创建成功", "data":{...}}，HTTP 200
  ▼
⑦ 响应原路返回：
  log_middleware 记录日志（方法/路径/状态码/耗时）→ 客户端收到 JSON
  ▼
⑧ 收尾：get_db 的 finally 执行 → db.close()（会话关闭，连接还给连接池）
  │
  └─ 如果中途抛异常：
       BizException        → biz_exception_handler（main.py）→ {"code":400/404,...}
       SQLAlchemyError     → db_exception_handler（main.py）→ {"code":50001,...}
       其他 Exception      → global_exception_handler（main.py）→ {"code":500,...}
       且 get_db 的 except 先 rollback() 再抛
```

### 8.2 数据怎么流转（注册 → 登录 → 用 token）

1. **注册**：`POST /auth/register`，body `{"username":"alice","password":"123456"}` → Pydantic 校验 → 查重 → bcrypt 加密 → 写库 → 返回 `{id, username, create_time}`（不含密码）。
2. **登录**：`POST /auth/login`，表单 `username=alice&password=123456` → 查用户 → `verify_password` 比对 → 签发 JWT（`sub="1"`，30 分钟过期）→ 返回 `{"access_token":"eyJ...","token_type":"bearer"}`。
3. **带 token 访问**：`GET /todo/1`，Header `Authorization: Bearer eyJ...` → `get_current_user` 验 token → 拿 user_id=1 → 查缓存 → 没命中查库（`user_id==1` 且 `id==1`）→ 写缓存 → 返回数据。

**user_id 的流转链**（必须能讲）：
`token 的 sub` → `jwt.decode` → `int(sub)` → `get_current_user` 查库确认 → `get_current_user_id` 取出 → 注入 todo 接口 → 所有查询都带 `filter(Todo.user_id == user_id)`。

## 第 9 章 报错定位手册：看到什么错，去查哪里

面试题"报错能定位层级"——**背这张表**：

| 你看到的报错 | 去哪查 | 原因和修复方向 |
|---|---|---|
| HTTP **401** "Not authenticated" | 请求头 | 根本没带 `Authorization` 头（`oauth2_scheme` 自动抛的）→ 带上 `Bearer <token>` |
| HTTP **401** "无效的认证信息" | `utils/auth.py` 的 `get_current_user` | token 伪造/过期/格式坏/`sub` 缺失/用户被删 → 重新登录拿新 token |
| HTTP **422** | `schemas/*.py` 或 `routers/*.py` 的参数 | Pydantic 校验失败：body 缺字段、类型错、长度超限、`page_num<1`、`page_size>100` → 看响应里的 `detail` 会精确指出哪个字段错了 |
| HTTP 200 + body `code:400` | `routers/auth.py`、`utils/auth.py` | `BizException`：用户名已存在 / 密码过长 / 用户名或密码错误 → 看 `msg` |
| HTTP 200 + body `code:404` | `routers/todo.py` | 待办不存在（查不到，或**不是当前用户的**）→ 检查 id 和 user_id |
| HTTP 200 + body `code:50001` | `main.py` 的 `db_exception_handler` + 服务终端 | SQLAlchemy 数据库异常：连不上 MySQL、SQL 错、约束冲突 → 看 uvicorn 终端的 Traceback |
| HTTP 200 + body `code:500` | `main.py` 的 `global_exception_handler` + 服务终端 | 未捕获的代码 bug → 看 uvicorn 终端的 Traceback，定位抛错的那一行 |
| 启动即失败，报 SECRET_KEY 错误 | `config/settings.py` 的 `_reject_insecure_secret` | `.env` 里 SECRET_KEY 还是默认值 → 改成强随机值（`openssl rand -hex 32`） |

**怎么看异常栈（Traceback）**：uvicorn 终端里报错时会打印一大段，格式是从下往上读：

```
Traceback (most recent call last):
  ...
  File "D:\...\routers\todo.py", line 62, in get_one        ← 自己代码的位置
    todo = db.query(Todo).filter(...).first()
  File "D:\...\sqlalchemy\...", line xxx, in first           ← 第三方库内部
    ...
sqlalchemy.exc.OperationalError: ...                          ← 最底层真正的原因
```

- **最后一行**是真正的原因（比如连不上数据库）；
- **往上找到第一个"你自己项目里的文件"**，那就是 bug 位置（第 9 章表格里的 `routers/todo.py` 那一层）。

**快速判断口诀**：
- 4xx 开头 → 是**客户端/参数/权限**问题 → 查 schemas 和认证逻辑；
- 5xx 开头 → 是**服务器内部**问题 → 查异常栈；
- body 里 `code:4xx` → 业务规则问题 → 查 routers 里的 BizException；
- `code:50001` → 数据库层 → 查连接和 SQL。

## 第 11 章 面试官可能追着问的"为什么"（底线延伸）

这些是从底线题自然延伸出来的，答好是加分项：

1. **为什么业务错误用 HTTP 200 + body code，而不是 HTTP 4xx？**
   答：前端只需统一解析一种格式；但代价是丢了 HTTP 语义（严格 REST 会认为该用 4xx）。能说出"好处 + 代价"才是真懂。

2. **JWT 和 Session 有什么区别？**
   答：JWT 无状态（服务器不存登录态，验签名即可，适合分布式）；Session 存服务端（可主动踢人，但多机部署要共享存储）。本项目用 JWT，所以"注销"做不了（token 到期前都有效）。

3. **缓存一致性怎么保证？**
   答：写操作（改/删/清空）时同步删 Redis 里的 key（先写库再删缓存）。风险点：删缓存失败会读到旧数据；极端并发下可能旧数据回填。本项目只缓存单条查询，风险可控。

4. **缓存穿透 / 击穿 / 雪崩？**
   答：穿透=查不存在的 key 全打到 DB（解决：缓存空值）；击穿=热点 key 过期瞬间被挤爆（解决：互斥锁）；雪崩=大量 key 同时过期（解决：过期时间加随机抖动）。

5. **外键 + 数据隔离的隐患？**
   答：每处查询都要手动带 `user_id` 条件，容易漏写。生产可用行级权限或 ORM 全局过滤器。

6. **为什么 `sub` 要 `str(user.id)`？**
   答：JWT 规范要求 `sub` 是字符串，python-jose 强校验，传整数会抛 `JWTError: Subject must be a string` → 变成 401。校验时再 `int(sub)` 转回来。

7. **中间件和异常处理器的区别？**
   答：中间件包住**所有**请求（日志/CORS/限流），在路由前后执行；异常处理器只接住**抛出的异常**，按类型分发。中间件里出错也会被异常处理器接住。
