## 一、项目架构全景（一句话讲清项目）

**一句话版本**：
> 这是一个 FastAPI 写的待办事项后端。用户先注册/登录拿到 JWT，之后请求 `/todo/*` 时带 `Authorization: Bearer <token>`，后端用 SQLAlchemy 存 MySQL、用 Redis 缓存单条查询，通过中间件记日志、用全局异常处理器统一返回 `{code, msg, data}`，最后用 Alembic 管表结构、Docker 一键部署。

**请求全链路（面试官常问"一个请求进来发生了什么"）**：
```
浏览器/客户端
   │  POST /todo/  +  Authorization: Bearer xxx
   ▼
log_middleware（记日志：方法、路径、状态码、耗时）        ← utils/logger.py
   │
   ▼
路由匹配（FastAPI 按注册顺序找对应函数）                  ← routers/todo.py
   │
   ▼
依赖注入：get_db() 给一个 DB Session
          get_current_user_id() 校验 token → 取出 user_id   ← utils/auth.py
   │
   ▼
视图函数：校验请求体(Pydantic) → 查库/写库 → commit
   │
   ▼
返回 success(data=...)  → 统一 JSON {code:200,msg,data}     ← utils/response.py
   │
   ▼
如果中途抛 BizException → biz_exception_handler 返回业务错误
         抛 SQLAlchemyError → db_exception_handler 返回 50001
         抛其他 Exception → global_exception_handler 返回 500  ← main.py
```

## 二、HTTP / 接口层（对应 routers/）

### 1. 这个项目用了哪些 HTTP 方法？各自语义？
| 方法 | 语义 | 项目中的用途 |
|------|------|------|
| GET | 查 | 分页查待办、查单条 |
| POST | 增 | 注册、登录、新建待办 |
| PUT | 改（整体/部分） | 修改待办 |
| DELETE | 删 | 删除待办、清空 |

**扩展**：`PUT`（整体替换）和 `PATCH`（部分修改）的区别。本项目的 `TodoUpdate` 字段全可空，用 `exclude_unset=True`，相当于 PATCH 语义但用了 PUT——可提一句这是可讨论的点。

### 2. HTTP 状态码本项目怎么用？
- 成功统一返回 **HTTP 200**，业务状态放在 body 的 `code` 字段（`utils/response.py` 的 `success`/`fail` 都返回 200）。
- 认证失败返回 **401**（`get_current_user` 抛的 `HTTPException`）。
- 请求校验失败由 FastAPI 返回 **422**（Pydantic 校验不过）。
- **注意**：本项目"业务错误"（如用户名已存在）返回 HTTP 200 + `code:400`，不是真正的 HTTP 400。这是一个**可被面试官挑战的设计点**——需要你能解释"为什么要用统一 code 而不是 HTTP 状态码"（前端解析统一、方便切协议），也要承认"严格 REST 会认为应该用 HTTP 4xx"。

### 3. 登录用表单，注册用 JSON，为什么？
- 登录接口声明 `form_data: OAuth2PasswordRequestForm = Depends()`，这是 **OAuth2 密码模式**的标准，Swagger UI 的 Authorize 按钮能识别 `tokenUrl` 并自动用表单提交。
- 注册接口用的是 Pydantic `UserCreate`，走 JSON body。
- **面试点**：`OAuth2PasswordRequestForm` 是 FastAPI 为 OAuth2 密码流提供的表单解析，字段名必须是 `username`/`password`。

### 4. FastAPI 依赖注入 `Depends` 怎么工作？
- `get_db()` 是生成器依赖，用 `yield` 在请求期间提供 Session，`finally` 里关闭。这就是 **依赖注入 + 请求作用域生命周期**。
- `get_current_user_id` 依赖 `get_current_user`，`get_current_user` 依赖 `oauth2_scheme`（从请求头读 `Authorization: Bearer`）。依赖可以层层嵌套，这是 FastAPI 的核心机制。

## 三、认证 / 安全层（对应 utils/auth.py、routers/auth.py）

### 5. JWT 是什么？为什么是无状态的？
JWT = JSON Web Token，三段式 `header.payload.signature`，用 `.` 分隔，Base64Url 编码。
- header：`{"alg":"HS256","typ":"JWT"}`
- payload：业务声明，本项目有 `sub`（用户 id）和 `exp`（过期时间）
- signature：`HMAC-SHA256(header.payload, SECRET_KEY)` 生成的签名，用于防篡改

**无状态**：服务器不存登录态，只要 token 签名合法、未过期就信任它。所以服务器**不用查数据库判断"是否登录"**（但 `get_current_user` 仍查库确认用户存在）。

### 6. 本项目 token 里存了什么？
`create_access_token(data={"sub": str(user.id)})` → payload 里有 `sub` 和 `exp`。
**你踩过的坑（重要谈资）**：JWT 规范要求 `sub` 是**字符串**，而 `user.id` 是整数。python-jose 解码时会强制校验 `sub` 必须是字符串，否则抛 `JWTError: Subject must be a string` → 变成 401。所以签发时 `str(user.id)`，校验时 `int(sub)` 转回。

### 7. 密码为什么要 bcrypt？为什么不直接存明文/md5？
- bcrypt 是**慢哈希**，故意算得慢，让暴力破解成本极高。
- 自带**随机盐**，同样密码每次哈希结果不同，防彩虹表。
- md5/sha256 是**快速摘要**，算得快，配合彩虹表很容易被破解；md5 还有已知碰撞漏洞。
- 你踩过的坑：bcrypt 只接受**最长 72 字节**，超过会抛异常（passlib 1.7.4 + bcrypt 5 的不兼容还导致整个哈希全挂）。所以项目里统一用 `_check_length()` 拦截超长密码返回 400，而不是让它变 500。

### 8. SECRET_KEY 为什么不能是默认值？泄露会怎样？
JWT 用 `HMAC-SHA256(header.payload, SECRET_KEY)` 生成签名，`SECRET_KEY` 是唯一的"密钥"。一旦泄露，任何人都能**自己伪造一个合法 token**（把 `sub` 改成任意用户 id 再签个名），从而冒充任意用户。所以 `settings.py` 里用 `model_validator` 强制 `SECRET_KEY` 不能是默认值。

### 9. 认证失败的两种"无效认证"区别？
- token 缺失 / 解码失败 / `sub` 缺失 / 用户不存在 → 抛 `HTTPException(401, "无效的认证信息")`。
- 业务层面（用户名或密码错）→ 抛 `BizException(400, "用户名或密码错误")`。

## 四、数据库层（对应 models/、db/base.py、alembic/）

### 10. SQLAlchemy ORM 是什么？和写原生 SQL 的区别？
ORM = 对象关系映射，把数据库表映射成 Python 类、把行映射成对象。你用 `User`、`Todo` 类操作，SQLAlchemy 帮你翻译成 SQL。优点：类型安全、跨数据库、防 SQL 注入（用参数化查询）。缺点：复杂查询不好优化（可用原生 SQL 或 `text()` 补充）。

### 11. 表结构是什么？有哪些关联？
- `sys_user`：`id`(主键自增)、`username`(唯一索引)、`hashed_password`、`create_time`
- `todos`：`id`、`title`、`description`、`is_done`、`create_time`、`user_id`(外键→sys_user.id)
- 关系：一个用户有多条待办（`User.todos` / `Todo.user`，`back_populates` 双向绑定）。

### 12. 外键和"用户数据隔离"怎么实现的？
- `todos.user_id` 外键指向 `sys_user.id`。
- 所有 `todo` 查询都带 `filter(Todo.user_id == user_id)`，`user_id` 来自 token 里的 `sub`。所以 A 用户永远查不到、改不到、删不到 B 用户的待办。
- **面试点**：这种"在每一层都带上当前用户条件"是数据隔离的正确做法；隐患是**容易漏写**，生产会用更严格的方案（如行级权限、ORM 全局过滤器）。

### 13. 事务、commit、rollback 是什么？
- 事务是一组要么全成功要么全失败的操作。`db.commit()` 提交，`db.rollback()` 回滚。
- 之前你项目的 `get_db()` 只 `close()` 不 `rollback`，遇到异常事务会悬挂。已改为：`except Exception: db.rollback()` 再 `raise`。
- `Session` 默认 `autoflush=False`，显式 `commit` 才真正写库。

### 14. alembic 是干什么的？upgrade/downgrade？
- Alembic 是**数据库迁移工具**：把模型变更转成可执行的版本化 SQL。
- `alembic upgrade head` 把库升级到最新版；`downgrade` 回退。
- 每个 `versions/` 文件有 `upgrade()` 和 `downgrade()`，`revision`/`down_revision` 串成迁移链。
- `env.py` 里 `target_metadata = Base.metadata` 告诉 alembic 看哪些模型，`get_url()` 从环境变量动态取连接串。

### 15. 为什么 `create_time` 用 `server_default=func.now()` + `default=datetime.utcnow`？
- `server_default`：在数据库层生成默认值（即使不走 ORM 也生效）。
- `default`：ORM 插入时由 Python 生成。
- 两个都设，保证无论哪条路径都有默认时间；用 UTC 保证跨时区一致。

## 五、缓存层（对应 db/redis_client.py、routers/todo.py）

### 16. 为什么用 Redis 缓存？缓存在哪几处？
- Redis 是内存 KV 数据库，读比 MySQL 快几个数量级，用来缓解高频读。
- 本项目只对"查单条待办"做缓存（`GET /todo/{id}`），key 是 `todo:{user_id}:{todo_id}`，过期 30 分钟。新建/修改/删除/清空时删除对应 key 保证一致性。

### 17. 缓存一致性是怎么保证的？（重点）
写操作时删缓存：`redis_client.delete(...)`（在 PUT/DELETE 里）。
- **先写库再删缓存** 是常见模式，但要能回答它的**两个坑**：
  - 删除缓存失败 → 下次仍读到旧数据（解决办法：延迟双删、消息队列重试）。
  - 读写并发竞态 → 极端情况会先删缓存后写库，导致旧数据回填（解决办法：加锁 / 缓存失效时间兜底 / 双删）。
- 本项目缓存只作用于单条查询，全量列表**没缓存**，所以整体一致性风险低。

### 18. 缓存穿透 / 击穿 / 雪崩是什么？
- **穿透**：查一个不存在的 key，每次都打到数据库。解决：缓存空值、布隆过滤器。
- **击穿**：一个热点 key 过期瞬间，大量请求同时打到 DB。解决：互斥锁、热点不过期。
- **雪崩**：大量 key 同时过期，DB 被打爆。解决：过期时间加随机抖动、多级缓存。
- 本项目单条缓存过期时间固定 1800 秒，量大时其实有"批量过期"隐患，可提一句改进思路。

### 19. 为什么 `clear_all` 用 `scan` 不用 `keys`？
`KEYS pattern` 会**全库遍历**、阻塞 Redis 单线程，量大时卡死服务。`SCAN` 是**游标分页**遍历，非阻塞。这是面试高频点。

## 六、异常处理 / 响应层（对应 utils/、main.py）

### 20. 统一响应格式 `{code, msg, data}` 有什么好处？
- 前后端约定一致，前端不用为每种错误单独处理。
- 业务错误（code 400）和系统错误（code 500）用 code 区分，但 HTTP 层都 200，方便前端统一拦截。
- **代价**：丢失了 HTTP 状态码语义，且某些 HTTP 客户端/网关无法区分成功失败。面试时能说出"好"和"不足"才是加分。

### 21. 全局异常处理器怎么用？（`main.py`）
- `@app.exception_handler(BizException)`：业务异常 → 返回 code=400。
- `@app.exception_handler(SQLAlchemyError)`：数据库异常 → 返回 code=50001。
- `@app.exception_handler(Exception)`：兜底所有未处理异常 → 返回 code=500（并把异常信息拼进 msg）。
- **面试点**：这种"分级异常处理"把"预期内错误"和"意外错误"分开，避免把内部细节暴露给用户；但兜底 handler 把 `str(exc)` 直接返回给客户端有**信息泄露风险**，生产应只记日志、返回通用提示。

### 22. 中间件是干什么的？（`utils/logger.py`）
- `log_middleware` 用 `@app.middleware("http")` 注册，每次请求进来算耗时、记录方法/路径/状态码。
- 中间件在**路由之前**执行，可以统一做日志、鉴权、限流、CORS 等。

## 七、工程 / 部署层

### 23. Dockerfile 和 docker-compose 分别干什么？
- **Dockerfile**：描述怎么把应用"打包成镜像"（基础镜像 python:3.11-slim → 装依赖 → 复制代码 → 启动命令）。
- **docker-compose.yml**：描述**多服务编排**（MySQL + Redis + API 三个容器一起启动、网络互通、数据卷持久化），`depends_on` + healthcheck 保证数据库就绪后再起 API。

### 24. 为什么 `.env` 不能提交？
`.env` 里有数据库密码、JWT 密钥等敏感信息。提交到 GitHub 等于公开密钥，任何人可伪造 token / 连你数据库。所以 `.gitignore` 忽略 `.env`，仓库只提交 `.env.example`（占位模板）。

### 25. 环境变量怎么管理？
`config/settings.py` 用 `pydantic-settings` 的 `BaseSettings`，从 `.env` 读取，带默认值。`extra="ignore"` 忽略多余项。这样同一套代码在不同环境（本地/容器）只需换 `.env`。

### 26. 你是如何部署的？CI/CD 是什么？（进阶）
- 部署：把代码放到一台有 Python/环境的机器，装依赖、跑 `alembic upgrade head`、用 uvicorn 起服务（或用 Docker）。
- CI/CD：用 GitHub Actions 在 push 时自动跑测试、自动构建镜像、自动部署。是简历里的重要加分项。

## 八、项目踩坑复盘（面试最有价值的部分，STAR 式讲）

把你实际遇到的问题整理成故事，面试官会很有兴趣。格式：**情境 → 任务 → 行动 → 结果**。

### 坑 1：注册/登录相关密码报 500
- **情境**：接口在特定场景返回 `500 服务器内部错误：password cannot be longer than 72 bytes`。
- **行动**：定位到依赖版本不兼容——`passlib 1.7.4`（已停止维护）与 `bcrypt 5.0.0` 不兼容，passlib 初始化时内部用 255 字节密码自检，bcrypt 5 直接抛异常，导致所有哈希操作都失败。改用直接 `bcrypt` 库，并把 72 字节校验统一收敛到一处，超长返回业务 400 而非 500。
- **结果**：问题消除，且更健壮（不再依赖过期库）。
- **可引申**：版本依赖管理、`bcrypt` 72 字节上限、慢哈希原理。

### 坑 2：登录后请求一律 401
- **情境**：拿到 token 后访问 `/todo/*` 始终 `401 无效的认证信息`。
- **行动**：解码 token 发现是 python-jose 强制要求 `sub` 为字符串，而签发时传了整数 `user.id`。修复：签发 `str(user.id)`、校验 `int(sub)`。
- **可引申**：JWT 规范、`sub` 声明、错误如何分层定位。

### 坑 3：`/todo/clear` 永远 422/无法命中
- **情境**：`DELETE /todo/clear` 总是返回 422 或匹配不到。
- **行动**：路由 `/{todo_id}`（int 类型）注册在 `/clear` 之前，FastAPI 按注册顺序匹配，把 `clear` 当 int 解析失败。把 `/clear` 移到 `/{todo_id}` 之前。
- **可引申**：路由匹配顺序、路径参数类型转换。
